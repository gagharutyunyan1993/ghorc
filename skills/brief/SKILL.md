# Бриф

Одна и та же структура для любой роли; меняется вопрос, не форма. Обычный бриф ≤500 слов, критичное ревью ≤800, >200 строк - ошибка постановки. Вызов Agent всегда с явным `effort`.

| Тег | Назначение |
|---|---|
| `<role>` | Кто агент и что он не делает (субагентов не запускает) |
| `<context>` | Зачем задача, что уже решено; без истории |
| `<read_first>` | Файлы и строки, с которых начать (`file:line`) |
| `<you_own>` | Что агент имеет право менять |
| `<steps>` | Что сделать, по порядку |
| `<constraints>` | Инварианты, запреты, команды проверок |
| `<report_back>` | Формат и длина отчёта |

## Наполнение по усилию
- low: правило, охват, проверка.
- medium: поведение и критерии готовности.
- high: инварианты и опасные сценарии.

## Стиль
- Для Sonnet: явные `file:line`; «каждый» только там, где действительно каждый; файл >400 строк - сначала вопрос.
- Команды проверок бери из `checks` конфига проекта (`.claude/orc-kit.json`); не выдумывай (`eslint --fix`, `prettier --write`).
- Не проси возвращать рассуждения. Крупное - в файл, в отчёте путь.
- Агенты читают `<проект>/CLAUDE.md` и конфиг сами; не пересказывай их в брифе.

## Шаблон 1. Исполнитель (`implementer`, medium или high)
```
<role>Ты исполнитель задачи <ID>. Работаешь сам, субагентов не запускаешь.</role>

<context>
<одно-два предложения: какое изменение поведения нужно и зачем>
Исходное дерево: <ветка / SHA>. Рабочий каталог: <worktree>.
</context>

<read_first>
- <file:line> - <зачем читать>
</read_first>

<you_own>
<файлы и модули, которые можно менять. Всё остальное - только в раздел «Предложения» отчёта.>
</you_own>

<steps>
1. <шаг>
2. <шаг>
3. Проверки: <команда checks.fast>
Готово, когда:
- <проверяемый результат>
</steps>

<constraints>
- <инварианты, совместимость, запреты (платные вызовы, релиз, чужие ветки)>
- Не расширяй задачу сопутствующим рефакторингом.
- Проверки только через <команда>; full и весь набор тестов не запускай; используй уже действительные результаты для того же дерева.
- После двух неудачных исправлений одной причины прекрати правки наугад: верни наблюдения, гипотезы и следующий шаг.
</constraints>

<report_back>
STATUS: DONE | HANDOFF | BLOCKED. Затем: SHA; изменение поведения; проверки с выводом и ссылками; непроверенное; блокеры; следующий шаг; предложения. До 25 строк, остальное - в файл <путь>.
</report_back>
```

## Шаблон 2. Критичный ревьюер (`reviewer-critical`, high, 1-й круг)
```
<role>Ты адверсариальный ревьюер <ID>. Продуктовые файлы не меняешь, субагентов не запускаешь.</role>

<context>
Диапазон: <base SHA>..<head SHA>.
Существующие доказательства: <результаты проверок, SHA/дерево, среда, ссылки>.
</context>

<read_first>
Начни с diff. Расширяй чтение по затронутым зависимостям, вызывающему коду и контрактам:
- <file:line>
</read_first>

<you_own>Файл ревью <путь>. Только он.</you_own>

<steps>
1. Проверь инварианты:
   - <инвариант>
2. Проверь опасные сценарии:
   - <сбой/повтор/восстановление, относящиеся к изменению>
3. Не повторяй действительный fast на том же дереве. Запускай только недостающие целевые проверки через <команда>.
4. Для каждой находки: серьёзность; file:line; нарушенное требование; условия; последствие; доказательство; минимальное исправление. Подтверждённый дефект отделяй от гипотезы. CHANGES_REQUIRED только при P0/P1 с file:line и воспроизведением.
5. Не добавляй новые требования ради улучшения архитектуры.
</steps>

<constraints>
- full и весь тест-раннер без аргументов запрещены.
- Бюджет не разрешает закрывать P0/P1.
</constraints>

<report_back>
Вердикт: ACCEPT / ACCEPT_WITH_NOTES / CHANGES_REQUIRED / BLOCKED.
Все обоснованные находки - в файл ревью. В ответе: блокеры, объём проверки, пробелы. До 30 строк.
</report_back>
```

## Шаблон 3. Механика (Haiku, low)
```
<role>Ты выполняешь одну механическую операцию. Не расширяй задачу и не запускай других агентов.</role>

<context>Зачем нужен результат: <одна строка>.</context>

<read_first>Вход: <конкретные файлы или данные>.</read_first>

<you_own>Результат: <формат или разрешённый diff / путь выходного файла>.</you_own>

<steps>
1. Сделай: <однозначная операция>.
2. Охват: <точные границы>.
3. Проверка: <команда или правило>.
</steps>

<constraints>При несовпадении входа с описанием - BLOCKED с причиной. Ничего не додумывай.</constraints>

<report_back>Результат в указанном формате; до 10 строк.</report_back>
```

## Антипаттерны
| Антипаттерн | Почему плохо |
|---|---|
| «Разберись в коде и предложи улучшения» (Sonnet) | Прочитает много файлов, вернёт общие слова |
| «Проверь всё» (Opus) | Запускает полный набор тестов в каждом круге |
| Бриф >200 строк | Дорогой старт и размытая задача |
| Просьба вернуть рассуждения | Выходные токены оседают в окне лида |
| Выдуманные команды проверок | Проверки идут только по `checks` конфига |
| Бриф без `file:line` для Sonnet | Агент ищет точки входа сам |

## Лимиты отчётов
Агент лиду ≤25 строк, ревью ≤30; крупное в файл, в отчёте путь. Лид владельцу: итог сначала, ≤25 строк.
