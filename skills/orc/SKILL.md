# Лид-оркестратор

Конфиг проекта: `.claude/ghorc.json` (проверки, критичные области, пороги). Роли плагина: `ghorc:implementer`, `reviewer`, `reviewer-critical`, `integrator`, `release`, `scout`, `consult`, `media`.

## Правила в одну страницу
1. Лид - Opus/medium; модель и усилие задаются при запуске явно (`--model opus --effort medium`), глобальный fallback роль не заменяет.
2. Исполнитель - Sonnet/medium; деньги, восстановление, миграции - Sonnet/high.
3. Обычное ревью и проверка правок обычного пакета - Sonnet/medium; критичное ревью - Opus/high в 1-м круге; на критичном пакете итоговый вердикт и проверка денежных находок - Opus/high, Sonnet проверяет только некритичные находки.
4. Opus повторно - если правка меняет денежный инвариант.
5. Haiku/low - только механика с машинно проверяемым результатом; не браузер, не разведка.
6. Fable - арбитр спорного вопроса или консультация; не лид и не ревью по умолчанию.
7. Мелочь (≤2 команды, вывод ≤100 строк, без правок кода пакетов) лид делает сам; больше - в файл или агенту.
8. При каждом вызове Agent передавай `effort` явно по таблице ниже; не полагайся на frontmatter и глобальные настройки.
9. Лид не читает PDF и изображения, транскрипты, логи и файлы >100 строк целиком (дифф - по `--stat` и по файлам). Вложения - файлом с путём роли `media`. PDF заранее в текст/PNG.
10. Лид не пишет код пакетов, не гоняет проверки синхронно, не опрашивает агентов.
11. Контекст лид читает командой `node "${CLAUDE_PLUGIN_ROOT}/scripts/ctx.cjs"` на границе этапа (файл пишет статус-строка; корень проекта из worktree определяется через `git rev-parse --git-common-dir`). Свой id сессии лид берёт из самого свежего файла `ctx-*.json` (`ctx.cjs` помечает его `*`) или из статус-строки, затем `ctx.cjs --session <id>`: `thresholds.ctxPrepare` (120K) - обновить STATE; `thresholds.ctxHandoff` (150K) - новый пакет не брать, skill `handoff`; ~170K - передача на ближайшей границе этапа.
12. Большой вывод не втягивать; если втянут - `/rewind` делает владелец. `/clear` у лида не применяется.
13. В чат ≤25 строк; отчёт агента ≤25 строк (ревью ≤30); крупное в файл.
14. Бриф - одна тегированная структура (skill `brief`); обычный ≤500 слов, критичное ревью ≤800; >200 строк - ошибка постановки.
15. Проверки только через команды из `checks` конфига; голый тест-раннер и `full` у агентов запрещены.
16. `full` - один на итоговом дереве, только лид, в фоне, после fast; incomplete - сначала причина, перезапуск только упавшей фазы.
17. Лимит ревью - 3 круга; второй `CHANGES_REQUIRED` - лид меняет постановку, а не шлёт того же исполнителя.
18. Суб-лида нет; по умолчанию прямые Agent; herdr-воркер - когда нужен свой процесс или интерактив владельца. Воркер стартует с `GHORC_ROLE=worker` (bash: `GHORC_ROLE=worker herdr agent start ...`; PowerShell: `$env:GHORC_ROLE='worker'; herdr agent start ...`), иначе он получит напоминание лида; кандидат-лид в `/handoff` стартует с `GHORC_ROLE=lead`.
19. Лимит: лид + 2 рабочих суммарно (агенты и воркеры вместе); одна тяжёлая проверка на машину.
20. «Существенное» для консультации - любой из признаков: деньги/данные/восстановление; внешний контракт или миграция; труднообратимая зависимость; конфликт ключевых требований; два неудачных подхода. Состав: собеседник + критик, один раунд.

## Маршрутизация
| Класс работы | Роль / модель | Усилие |
|---|---|---|
| Лид | Opus | medium |
| Исполнитель обычный | `implementer` sonnet | medium |
| Правка по готовому образцу | `implementer` | low |
| Деньги, восстановление, миграции | `implementer` | high |
| Архитектура с понятными ограничениями | Opus | medium (конфликт инвариантов - high) |
| Ревью обычное, проверка правок | `reviewer` sonnet | medium |
| Ревью критичное (контракт, политика, хук, деньги) | `reviewer-critical` opus | high |
| Разведка (факты о коде, git) | `scout` sonnet | low-medium |
| Механика с машинной проверкой | Haiku | low |
| Вложения (PDF, снимки) | `media` sonnet | low |
| Консультация во внешних моделях | `consult` sonnet | low |
| Спор, арбитр | Fable, точечно | medium-high |
| Конфликт слияния, красный пайплайн | `integrator` | medium |
| Релиз (только по слову владельца) | `release` | medium |
| Свой процесс или интерактив владельца | herdr-воркер, `--effort` явно | - |

## Усилие
- low: механика, разведка, правка по образцу. medium: всё штатное. high: критичное ревью, тонкая отладка, конфликт инвариантов, деньги - по названной причине. xhigh/max: только вручную на одну задачу.
- Эскалация: риск известен заранее - сразу нужные модель и усилие; неожиданная сложность - сначала переформулировать задачу, потом поднять effort, потом сменить модель; сбой сети, нехватка памяти, неверная команда - effort не поднимать.
- Убедись, что переменная `CLAUDE_CODE_EFFORT_LEVEL` не задана: она перебивает frontmatter и вызов.

## Лид никогда
- не читает PDF и изображения; не читает транскрипты, логи и файлы >100 строк целиком;
- не пишет код пакетов; не гоняет проверки синхронно; не опрашивает агентов (ждёт фоном);
- не измеряет свой контекст сам (только `ctx.cjs`); не применяет `/clear`;
- не просит «верни рассуждения» (выходные токены оседают в окне).

## Пороги и состояние
- STATE.md (шаблон `templates/STATE.md`) 40-80 строк: пакет и стадия, ветка и SHA, процессы, решения, блокеры, проверки, полномочия, необработанное. Источник истины - STATE, не разговор.
- Ожидание фонового `full` лид может простаивать долго: просыпаться по уведомлению, не опрашивать.

## SendMessage или новый агент
- Уточнение по той же задаче (≤5 вызовов, не позже часа) - SendMessage тому же агенту. Иначе - новый агент по диффу. Второй `CHANGES_REQUIRED` - новый бриф.
- Агент оборван по `maxTurns` (partial): возобновить один раз, затем BLOCKED. Исполнитель >120 запросов - диагностика; >150 - решение: завершить, передать этап или заблокировать.
